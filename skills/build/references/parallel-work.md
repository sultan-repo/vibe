# Automatic parallel work

Delegate substantial independent work only when the saved time warrants the extra context and coordination. Keep one coordinator; do not add a scheduler, mandatory team or task register.

## Plan capacity, then assign

- Identify the work that benefits from delegation, then choose each agent's role, scope and effort from its assignment. Launch as many ready independent assignments as the task requires; Vibe sets no fixed team size, starting count or numeric ceiling. Respect available runtime slots, isolated ownership, shared resources and existing owner usage/time constraints. Include integration effort when estimating time saved. Do not force artificial waves, a new budget question or an approval just to size the team; the coordinator decides. Keep small or tightly coupled work local.
- Count all active Vibe workers, including nested workers, against one coordinator-managed budget. Workers may not delegate further without an assigned slot and runtime support. Reuse a suitable worker for follow-on work when that saves context. When the runtime refuses another worker, continue available work and wait for capacity; do not retry repeatedly or change host limits.
- Reconsider the count when work finishes, dependencies change or a shared resource becomes a bottleneck. Add workers for newly ready work; reduce new assignments when resource waits, conflicts or coordination erase the benefit. Use existing completion/blocker reports, not a new scheduler, classifier, benchmark or polling loop. More workers do not create more review or full-verification gates.
- Assign only ready inputs and compatible ownership. Establish shared API/schema decisions first; different filenames alone do not establish independence. Release dependent tasks as their inputs become ready, without artificial rounds.
- Before assigning build/browser-dependent work, verify that the intended worktree can run the project's production build and browser checks. Reuse a proven setup until relevant tooling or environment changes; otherwise perform one bounded preflight during planning, not when a final gate hangs.
- If dependency symlinks fail, use real dependencies per worktree or a second full checkout when resources permit. With only one usable checkout, reserve one build/browser slot at a time with a time budget. Other workers continue coding or unit/integration work; do not serialize all engineering around that slot.
- Give each worker a short brief: objective, relevant constraints, source paths, interfaces, owned files, starting SHA, focused checks and any time/resource budget. Avoid copying whole histories or unrelated documents. Workers keep the coordinator's scope and permission limits and never publish, merge or deploy independently.
- In Codex use a native worker only when delegation is available and authorized. In Claude Code prefer the scoped `vibe:worker` (`worker` with the installer), which inherits the model and defaults to medium effort. Select effort by the assigned work: low for mechanical tasks, medium for ordinary implementation, high for hard reasoning or consequential invariants. For non-fork agents, pass the native per-invocation `effort` when exposed (Claude Code 2.1.292+); it overrides the agent default. Do not assume an unrestricted conversation fork accepts independent effort, or that an unconfigured agent inherits a skill's temporary override. Keep the current model unless an available alternative is justified and permitted.
- Host/environment overrides and caps still apply. A concise brief alone does not lower runtime effort. Reuse available metadata to distinguish requested from effective settings; if controls are unavailable, use bounded work and disclose a material limitation without requiring user commands. Do not spawn a worker solely to change effort.
- Keep the coordinator productively occupied. If delegation is unavailable or adds overhead, proceed locally without user setup or commands.

## Protect shared resources

- Prefer worktrees for substantial edits, verifying each starting SHA against the intended committed base. Uncommitted parent edits are absent; preserve them and deliberately supply authorized prerequisites or keep dependent work local.
- A shared checkout is suitable only for disjoint edits with exclusive ownership. Stop a worker before transferring its files. Worktrees do not isolate ports, databases or services; isolate those resources or reserve their use.
- The coordinator owns shared lockfiles, branch operations, integration, decision logs, status files and the plan. Workers never edit shared status; they return proposed decision/status text in their reports. Before launching substantial work, the coordinator records active packages and branch names, then combines reports at the core's state-change triggers rather than waiting for merges. Delimited blocks in the same shared file do not prevent conflicts.

## Long verification without blocking independent work

Run expensive verification in a stable committed candidate checkout when isolation and capacity make it useful, not at every milestone by rule. Continue independent edits elsewhere. Worktrees do not isolate ports, databases, fixtures or services; reserve or isolate them and serialize conflicting browser/build stages. Prefer verifying and promoting from the same candidate worktree because the optional cache is worktree-local.

The coordinator collects exit status, failures and cancellation, and saves discoverable run metadata for handoff. Pending, failed or cancelled checks never permit promotion. Evidence-only enforcement can reject a push without launching a suite inside the hook; arrange the separate verification path first. Foreground execution is valid when resources or the runtime cannot support safe background work. Do not add a scheduler or cross-worktree evidence store for this policy.

## Budget performance work

Set the fixture, success threshold, device profiles, maximum candidate cycles and time budget in the brief. Build once per candidate and reuse that artifact across measurements. Iterate on the cheapest representative profile; capture a baseline and a bounded final measurement session on target devices. Desktop-first suits general desktop work; mobile-specific problems need mobile evidence early. Stop at the agreed target. If the budget is exceeded, report results and replan before more experiments; do not hold the shared checkout indefinitely or claim an unmet target passed.

## Integrate once, verify at the right boundary

- Workers return their branch/patch, changed files, exact focused checks/results and blockers. Completion is not acceptance evidence. Inspect and integrate their work, resolving failed assignments within scope rather than repeatedly respawning workers.
- Use affected/expanded checks during increments under `testing-policy.md`. Re-evaluate cumulative dependencies against the current target-branch base after integration; worker-local passes do not prove the combined result. Feature completion alone does not require full E2E. Run the full integrated gate before formal production release/promotion, for unbounded impact or an explicit project integration gate, reusing valid evidence instead of repeating it per worker or push. Routine feature deployments use feature-scoped affected/expanded and deployment smoke/rollback checks, including auto-deploying merges. No automatic whole-journey E2E for small features.
- For a declared dependent stack, lower branches get required affected/expanded checks; a formal integrated release candidate gets the full gate. Do not ship dependent lower branches before their prerequisites. A routine branch deployed independently needs its own affected/expanded and smoke/rollback checks, not automatically the full E2E suite. Evaluate the cumulative diff after integration; quick successive merges do not prove isolation.
- Finalize tracked edits, stop concurrent writes and commit the candidate before the full gate. Keep verification evidence in Git-private storage or CI/PR records so recording results does not change the tested tree. Never pre-mark an unobserved outcome verified. Reuse valid evidence for unchanged inputs; integration changes invalidate the affected evidence.
- When high-risk behavior or an explicit request requires review, use one consolidated fresh-context independent review of the final HEAD and the bounded targeted recheck in `review-loop.md`. Do not review each worker. Test reuse does not broaden review approval or bypass required CI. External actions retain their existing authorization requirements.
