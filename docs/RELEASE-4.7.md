# Vibe v4.7.0 verification

## Scope

This candidate implements lighter milestone delivery, automatic native effort selection, progress updates for nontechnical owners, selective review, adaptive parallel work within resource limits and optional reuse of project verification. It changes Vibe only; it does not modify family-network or its deployment settings. Merge and publication have not been performed for this candidate.

## Evidence

Local candidate checks passed:

- `python3 -m unittest discover -s tests -v`: 32 tests, including 19 verification-cache regressions and native effort metadata contracts.
- `node --test tests/*.mjs`: 17 board/benchmark tests, including plain default activity, optional technical details, retained Arabic task labels and truthful waiting/finished states.
- `python3 hooks/test-force-push-hook.py`: all 28 safeguards.
- Shell/JSON/YAML syntax, matching project templates and exact startup-hook injection.
- Isolated install, reinstall and uninstall preserved personal files/settings and did not register a global verification gate.

Native strict plugin validation and Mod render tests run on the release PR and on main using pinned Claude Code 2.1.314. The Claude CLI is absent from the local executor; the pull request's CI records those outcomes rather than claiming a local native run.

The cache tests exercise real temporary Git repositories, including actual pre-push ref input, clean/dirty snapshots, full/quick reuse, context changes, failed verification and linked worktrees. They establish helper behavior, not the correctness of a project's adapted gate or its declaration of ignored/environment inputs.

A fresh-context read-only exercise covered an interim UI fix, constrained parallel workers, same-tree release, performance work with a migration, a progress question and a documentation-only release. It identified two wording gaps, resolved by making document-only E2E applicability explicit and using a bounded targeted confirmation for a changed commit identity with otherwise unchanged reviewed scope.

The core, Build and Reassess sources together changed from 3,409 to 2,721 whitespace-delimited words (about 20% less); the always-loaded core changed from 1,333 to 1,263 words (about 5% less). These counts include effort selection, adaptive parallelism and nontechnical communication in those three files and exclude separately loaded skills/references and their discovery metadata. Word counts measure source size, not model billing tokens or runtime performance; earlier percentages described earlier candidates.

Native effort controls use medium workflow/worker defaults, a high reviewer default and three inline internal low/medium/high skills. Metadata tests establish the requested settings, inline model invocation and absence of additional tool grants or model changes. Installation checks cover their presence and cleanup. Workflow transitions apply the chosen effort after loading, while short answers avoid extra routing calls. Non-fork per-invocation worker overrides require a supported runtime; conversation forks are not promised independent control.

Progress wording is generated by the coordinator in the user's language, using outcome labels from the outset. The board preserves supplied labels, uses simple activity categories and hides tool/source identifiers behind Details. It makes no translation/model calls, adds no progress events or polling, and does not infer readiness from finished steps. Node tests cover state rendering; the native Mod test covers the updated empty state. Neither establishes live conversational compliance or a real interactive display.

Parallel work derives the agents, their roles, effort and number from the task. Vibe imposes no fixed team size, starting count or numeric ceiling; existing owner constraints, host slots, dependencies and resources still apply. A bounded read-only policy check covered actual host capacity, separate build/browser reservations and lightweight coordinator budgeting. It is not evidence of live automatic team sizing or a measured speedup.

## Disclosed limits

Authenticated Claude execution and comparative elapsed-time/token measurements have not been run. A read-only scenario exercise checks policy consistency; it does not establish that live Claude always follows the policy. In particular, effective effort under the owner's host is unverified: native configuration can be superseded by environment/host controls or caps, and reading a skill as a fallback cannot activate its metadata. Adoption should confirm effective settings from available runtime evidence once and compare completed work including repairs, without adding per-task benchmarks. Interactive UI behavior remains unobserved for this version. The optional cache is not enabled in projects automatically and cannot infer every external verification input.

## Publication

The publisher accepts only a successful trusted main-push check run, verifies its exact source SHA, and creates/verifies the matching release tag. The published GitHub release adds the tested commit and CI URL. A passing release PR alone does not publish.
